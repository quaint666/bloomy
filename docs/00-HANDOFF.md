## 0. Things to know before touching anything

1. **Project:** Bloomy, a Vietnamese flower e-commerce site, a university course project. Live: https://bloomy.quaintshomelabdomain.uk.
2. **Language:** English with H; the site UI and all customer-facing text are Vietnamese.
3. **Stack:** Node 26 / Express 5 / PostgreSQL 18 / Docker / Cloudflare in front. Plain HTML + CSS + classic JS (no framework; the build steps are the **esbuild minify stage** (browser files) and the **tsc compile stage** (server), both in the Dockerfile, section 5). Schema is declarative with **pgschema** 1.13.1 (`schema.sql` is the desired state; never hand-ALTER production). Customer pages are not served as static files: `render.js` reads each page, inserts the shared partials (`<!--include:header-->` …) and fills `{{tokens}}` from the database before sending it.
4. **Everything customer-typed is rendered with `textContent` / `escapeHtml`; the CSP is strict:** `script-src 'self' https://www.googletagmanager.com`, `style-src 'self'`, `img-src 'self' data: https://*.google-analytics.com https://*.googletagmanager.com`, `connect-src 'self'` + the three Google hosts. **No inline styles or scripts**, no hotlinked images.
5. **"No repeated hardcoded values"** is a hard rule from H. One place per value (settings table, one module, one constant). The GA Measurement ID lives only in `web/main.ts` (its bundle is `public/js/main.js`); header/footer live only in `partials/`; footer categories come from the DB.
6. **jsdom cannot see CSS or layout.** This hid three real bugs (a `hidden` panel that never hid, an absolutely-positioned hint class used outside its container, a doubled scroll offset). Defence in place: a global `[hidden] { display: none !important }` rule, static CSS checks in `ui_polish_test`, and the rule **"say plainly what looks/feels cannot be verified"**. Never claim a visual result.

## 4. What was built (by batch, with the decisions behind it)

**3c / deploy session (2026-10-07).**
- **Owner 2FA** (`totp.js`, `routes/admin-auth.ts`, `admin-account.html` + `web/admin-account.ts`, `admin-login.html` + `web/admin-login.ts`, `css/admin-twofa.css`): RFC 6238 TOTP (SHA-1, 6 digits, 30 s, ±1 step of clock drift). The secret is stored **encrypted with AES-256-GCM** under the env variable **`TOTP_ENCRYPTION_KEY`** (32 random bytes, base64: `openssl rand -base64 32`). `server.js` lists it in `REQUIRED_ENV` and calls `require("./totp").loadKey()` at start-up, so a missing or wrong-length key stops the app with exit 1 and a clear message instead of failing at the owner's first login. A key that has the right length but is the **wrong key** (changed or lost) is caught only by a start-up self-check in `server.js` (`checkTotpKey`): it tries to decrypt one stored secret and logs one `Bloomy: ERROR: TOTP_ENCRYPTION_KEY cannot decrypt…` line; it never stops the app, it is not awaited (the line can come after the first `/healthz`), and it is silent when no secret is stored or the database is not ready. **Login is one request** carrying username, password and, when asked for, the code: right password + 2FA on + no code → `200 {needs_code:true}` and **no session**; a wrong code counts only after the password was right; **3 wrong codes lock that account for 5 minutes (in memory — a restart clears it)**; a code works **once** (`admin_users.totp_last_step`); 10 recovery codes, stored hashed, single use (`recovery_codes.used_at`); the 2FA endpoints share `twoFactorLimiter` (10 per 15 minutes). No "remember this browser" (decided). Manager/employee accounts have no 2FA.
- **Way back in when phone and codes are both lost:** `node create-admin.js --reset-2fa` (shell only, on the server: `sudo docker exec -it bloomy_app node create-admin.js --reset-2fa`). **[user-confirmed]** it works. After a reset the owner logs in with the password alone and enrols again.
- **Browser TypeScript (all 26 scripts converted, 2026-11-14):** every page script lives in `web/*.ts` (shared helpers in `web/lib/`); `shared/` holds the types the server and the browser both read (type-only, written for the JSON on the wire). `npm run typecheck:web` checks them and `npm run build:web` bundles each `web/*.ts` into `public/js/<name>.js` (esbuild, one classic script per page script, `--format=iife` so its names cannot clash). Stage `assets` runs both before the minify step below, so a type error in `web/` fails the image build. `web/package.json` (`"type": "module"`) is needed: with the root `"type": "commonjs"`, esbuild wraps every `.ts` module in CommonJS helper code. The bundles in `public/js/` are build output (gitignored, one `.gitignore` line each; `git ls-files public/js` is empty). `main.ts` is bundled on its own and exposes `window.Bloomy`; the other scripts read it through the `BloomyApi` type (an erased `import type`), so it is not repeated in each page. Test seams: a function a suite calls by name on `window` is assigned there explicitly (`afterLoginTarget`, `updateCartBadge`, `showPaymentWaiting`, `pollPickups`, `readingProgress`), and `pollTimer` is a live getter, because `checkout_live_test` and `landing_live_test` stop the poll with `eval`. Values both sides use are written once in `shared/rules.ts` (`MAX_QUANTITY`, `ROLE_RANK`, `ALLOWED_FULFILLMENT_TRANSITIONS`, `WINDOW_TEXT`, `WINDOW_END_MINUTES`, `DEFAULT_CUTOFF_HOUR_VN`), `shared/vn-time.ts` (the +7 h helpers) and `shared/escape.ts`; the order email keeps its own `escapeHtml` (it writes "" for a missing value where the shared one writes "null"). What the types do **not** check: the SQL (`pool.query<T>` is an assertion), what `res.json()` really sends (the reply bodies are checked on the server against `shared/api-types.ts`, the browser trusts them), and `localStorage` (the cart is read as written).
- **Minify:** the `Dockerfile` has three stages. Stage `assets` runs `npm ci --ignore-scripts`, the `web/` build above, and `esbuild --minify --charset=utf8 --legal-comments=none --outdir=/out --outbase=public` over `public/**/*.js|css` (with file-count checks); the final stage does `COPY --from=assets /out ./public` and also copies `totp.js`. esbuild is a **devDependency pinned in `package-lock.json`**. Not minified: HTML, `partials/`, `content/`. A new root-level `.ts` file needs its compiled `.js` added to the `COPY` edit (this is how `totp.js` was added).
- **Asset fingerprinting (replaces "purge Cloudflare after every deploy" for customer pages).** Why it was needed: Cloudflare sends browsers `cache-control: public, max-age=14400` (Browser Cache TTL 4 h) for static files, and `cf-cache-status: REVALIDATED` showed the *edge* was fine — the stale copy sat in the **browser**, which a purge cannot reach. Fix in `render.js` (applied after `expandIncludes`, before `fillTokens`): every relative `href|src="css/<name>.css"` / `"js/<name>.js"` in a rendered page gets `?v=<first 8 hex of the file's sha1>`; the hash is cached per file by mtime+size; the query string is part of Cloudflare's cache key, so a changed file gets a new URL at the edge **and** in the browser. **Not covered:** admin pages (served raw by `express.static`, so they can still be stale for up to 4 h after a deploy — hard-reload or purge), images (7-day max-age), root-relative `/js/…` URLs, URLs that already carry a query; a file that does not exist is left as written. That the origin sends `max-age=0` for static files is **inferred** from the code, not read off the wire.
- **Mobile/CSS fixes:** toast layout at ≤ 600 px, the campaign chip at ≤ 600 px, the landing card's "added" label positioned absolutely under the card (`.landing-card` is `position: relative` with 40 px bottom padding). The page cross-fade (`@view-transition`) was **removed**.
- **Cloudflare Bot Fight Mode** injects an inline script into every page, which triggers **one CSP console message per page**. Accepted: its content changes per request, so it cannot be hashed or allowed. Do not "fix" it by loosening `script-src`.
- **GA4 verified end to end** on the live site (loader, hits answered 2xx, nothing sent from admin pages, the order token not in any Google URL). The first-party `funnel_events` table is the source that ad blockers cannot hide — **state that limitation in the report's analytics chapter** (GA undercounts visitors with blockers).

## 5. Architecture and code map

**Request flow for a customer page.** `server.js` mounts helmet (CSP), sessions (`connect-pg-simple`, 1 h cookie, `secure` only when `NODE_ENV=production`), `trust proxy 2`, then **`app.use(pageRenderer())`** (handles `/`, `/landing`, `/blog`, `/blog/<slug>` and every `/<name>.html` except `admin-*.html`), then `express.static` (fonts immutable 1 y, images 1 week, everything else revalidated), then `sitemap.xml`, `/healthz`, the API routers and the error handler (the order in `server.ts`). Admin pages are plain static files (their header is built by `public/js/admin-nav.js`).

**Server modules**
- `render.js` — the page renderer: reads `public/<page>.html`, replaces `<!--include:name-->` with `partials/name.html` (nesting up to 5 deep), replaces `{{token}}` (escaped unless the token is in `RAW_TOKENS`, whose HTML render.js built itself). Checks `partials/` at startup. Product pages get server-written SEO tokens; `/landing` and the homepage campaign card come from `getActiveCampaign()`; blog pages from `blog.js`. Files are read from disk on every request. It also fingerprints `css/` and `js/` URLs (`versionAssets`, section 4).
- `blog.js` — builds `/blog` and `/blog/<slug>` from `content/` (`posts.json` is the source of the index **and** the sitemap), `[[product:N]]` → live product cards, `checkContent()` at startup. `BLOOMY_CONTENT_DIR` overrides the folder (tests only).
- `seo.js` — `effective()`, `checks()`, `snippet()`, `health()`, `cleanFields()` (one implementation for the panel and the page).
- `pricing.js` — **the only place money, coupons, shipping and custom-bouquet rules are computed** (`quote()`).
- `routes/orders.ts` — `placeOrder()` (the ONE order writer; web checkout and POS both use it), ZaloPay start/IPN/verify/retry, `returnOrderStock()`, `markOrderPaid()`.
- `routes/admin-auth.ts` — login (with the optional 2FA code)/logout/me/password, the owner-only 2FA endpoints (`/api/admin/me/2fa…`), `requireRole(level)`, `requireAdmin` (= manager+), `LANDING` per role.
- `totp.js` — TOTP/HOTP on `node:crypto`, AES-256-GCM secret encryption, recovery-code helpers; `loadKey()` reads and checks `TOTP_ENCRYPTION_KEY`.
- `routes/campaigns.ts` — `GET /api/campaigns/active` and `getActiveCampaign({ includeProducts })`.
- `routes/admin-campaigns.ts` — campaign editor API (picture list = real files in `public/images`, `BLOOMY_IMAGES_DIR` overrides for tests; validation; transaction for the product list).
- `routes/admin-seo.ts` — SEO panel API (list with health, one, patch, live preview).
- other routes: products, categories, tags, flowers (builder data), reviews, settings, admin-* (users, settings, coupons, pos, orders, products, flowers, stats, cutoffs, reviews), `csv.js`, `events.js` (funnel).
- `email.js` — customer + shop emails (`EMAIL_MODE=log` prints instead of sending).
- `create-admin.js` — bootstrap/emergency CLI (also how the first owner is made after a wipe); `--reset-2fa` clears an owner's 2FA.

**Folders:** `partials/` (header, nav-links, footer, floating-contact, checkout-form, checkout-payment) · `content/` (blog) · `public/` (pages, `css/`, `js/`, `images/`, `fonts/`) · `routes/` · `tests/` (not in the image).

**Frontend scripts.** `web/main.ts` (bundled to `public/js/main.js`) = cart, `quote`, project notice, GA loader, toast, `copyText`, recently-viewed storage, back-to-top, nav search, `data-copy` handler; exports `window.Bloomy.*` (`cart`, `escapeHtml`, `quote`, `toast`, `copyText`, `recent`, `track`, …). Per-page scripts, one bundle each: `home.ts`, `listing.ts`, `product.ts` (+ `lib/product-extras.ts`, imported by it), `cart.ts`, `checkout.ts`, `confirmation.ts`, `landing.ts`, `custom-bouquet.ts`, `blog.ts` (reading bar), admin pages `admin-*.ts`.

**Dockerfile** (three stages: assets, compile, runtime; section 4) copies the compiled output of: `server.js db.js email.js pricing.js render.js blog.js seo.js totp.js create-admin.js`, `routes/`, `shared/` (runtime values: `rules.js`, `vn-time.js`, `escape.js`), `public/` (the minified copy from stage 1), `partials/`, `content/`. **A new root-level `.ts` file or folder needs a COPY edit (`types.ts` excepted: types only)** (CI's start-up check catches a forgotten one). New files under `routes/`, `public/`, `partials/`, `content/` need nothing. Verified here: with no environment the app exits 1 with "missing required environment variables" (CI's fail-fast step), and with a missing `content/` it stops with a clear `ContentError`.

**Seeds, in load order:** `seed-categories.sql`, `seed-flowers.sql`, `seed-products.sql`, **`seed-gallery.sql`**, `seed-reviews.sql`, `seed-reference.sql`, **`seed-products-2.sql`**. `seed-reference.sql` must come **after** products (campaigns pick products by SKU; it raises an exception if it does not insert exactly 12 `campaign_products` rows), and `seed-products-2.sql` comes **last** because it also adds four campaigns (Tết, Valentine, Trung thu, Giáng sinh, each with a 20% coupon, six products and a picture) after the two campaigns of `seed-reference.sql`, which have fixed ids. `gen_products.py` generates `seed-products.sql` (statuses live there); `gen_products2.py` generates `seed-products-2.sql`: 54 more products for Peekbox's six occasions (BLM-0052 to BLM-0105, prices from stem cost like the first seed), the six `occasion` tags in calendar order, the occasion links of the first 50 products, and the four campaigns above (the coupon windows are a draft for the owner; a picture is set on the two older campaigns only where they have none). That file is **additive and idempotent** (no fixed ids, SKU and (kind, name) lookups, `ON CONFLICT DO NOTHING`), because it also has to reach a live shop, which never re-runs the first seed: `seed-more.sh` (schema image) runs just that file in one transaction against a database that already has the first catalogue, and a second run changes nothing. Seeds are for empty databases only: `seed.sh` (in the schema image, next to the seven files) loads them in this order in **one transaction, all or nothing**, and refuses, changing nothing, when `products` or `settings` already hold rows.

## 6. Decisions that are LOCKED (do not reopen without the user asking)

### 6.1 Money, shipping, coupons
- Prices are **tax-inclusive**. VAT rate in `settings.vat_rate` (10), shown as "Đã bao gồm VAT X%" and **copied onto every order**; only admin sees the VAT amount. The browser never computes money — `POST /api/orders/quote` prices everything. Stats revenue = subtotal − discount.
- Delivery fee by **ward ring** (101 wards from GHTK's list): `ring1/2/3_fee` = 25.000 / 35.000 / 45.000đ in settings. Pickup is free. GHTK is named; the **tracking code is typed by hand** in the admin order detail; an internal **admin note** is never shown to customers.
- **Coupons:** seeded `BLOOMY50` (fixed 50.000đ, minimum 800.000đ), `PHUNU20`, `THAYCO20` (percent 20, no minimum, date windows above). Code `^[A-Z0-9_-]{3,20}$`; code/type/value/minimum **locked after creation**; only `active` and the date window change; the window is checked against the **delivery date**; one coupon per order; applies to goods, not shipping; percent rounds down; never deleted.

### 6.2 Orders and stock
- `fulfillment_type` delivery (COD / ZaloPay) or pickup (cash / ZaloPay); `channel` web or pos. Bank transfer was dropped. Names and phones mandatory; email optional.
- **Stock is taken at placement** in one transaction (`UPDATE flowers SET stock = stock - n WHERE id = x AND stock >= n`, plus `CHECK (stock >= 0)`); returned only when an order still "new" is cancelled (once, from its own `order_item_flowers` snapshot). Shortage is shown **by flower name, never as a count**.
- Payment: pending / paid / failed / refunded. Fulfillment: new → delivering → delivered, or cancelled. "Delivering" needs a paid ZaloPay order; "delivered" auto-marks COD/cash as paid. Refund = paid → refunded (manager+); refunding an order that is still "new" also cancels it and returns its stems to the stock (once), refunding one already out for delivery or delivered leaves its status and stems.
- Availability: default cutoff + per-date overrides ("Giờ chốt đơn"), windows morning/afternoon/evening, `sold_out_today`, `discontinued`; web checks logged to `availability_checks`.
- Single-size products store **no size** on the order and show none anywhere.
- The staff order list loads the newest **1000** orders (`ADMIN_ORDER_LIST_LIMIT`, `shared/rules.ts`) and says so when it hits the cap; `orders.csv` has every order. The CSV guard prefixes a cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return with a quote.

### 6.3 Roles, admin, security

Sessions last 1 hour. Private windows share ONE cookie jar (use different browsers/hostnames to test roles side by side). **A site-wide backstop (2026-11-22):** every page and API route also shares one cap of 3000 requests per address per 15 minutes (`SITE_REQUESTS_PER_15_MIN`, optional, a whole number of 10 or more; pictures, styles, scripts, fonts and `/healthz` are not counted; the figure and the exemptions are in `routes/site-limit.ts`). Sessions last 1 hour. Private windows share ONE cookie jar (use different browsers/hostnames to test roles side by side).

## 9. SCHEMA, SEEDS AND RUNTIME FACTS

Technical facts kept from the original deploy record. The plan gate and the hosting they refer to are not part of this repo.

- CI is `.github/workflows/build.yml` (GitHub Actions, hosted runner): it builds the app and schema images, applies `schema.sql` to a throwaway PostgreSQL and requires an empty `plan`, runs every suite from source on the Dockerfile's Node, and on `main` pushes both images to GHCR tagged with the first 12 characters of the commit.

- Schema: a fresh database ends with an empty `plan` after `apply` (what CI checks). An in-place upgrade of an old database is additive only (new tables and columns, changed defaults, no `DROP`), but it creates no campaigns, no coupons and no status changes: seeds are not re-run on a live database. **Enum values are only ever added, never removed or reordered:** `plan` cannot see a removal or a reorder, so neither the plan review nor the deploy gate would catch it.
- Seeds, in this order, for empty databases only: expected counts afterwards are products 105 (100 listable: five are discontinued), product_sizes 247, recipes 631, product_tags 479, campaigns 6, campaign_products 36, coupons 7 **[verified 2026-11-22 on the local database; that `seed-more.sh` on a database with only the first 51 products gives the same counts was verified 2026-11-20, before the four extra campaigns, and not re-checked]**. They reach the server inside the schema image: after a wipe and a schema `apply`, run `/seed.sh` from that image (the command is in the header of `seed.sh`). A second run refuses with "this database already has data… Nothing changed.". For a **live** shop that has only the first catalogue, run `/seed-more.sh` instead (same connection variables; run the schema `plan` and `apply` first, the occasion tags need the new `tag_kind` value): it refuses on an empty database and prints how many products it added (0 on a second run).
- `TOTP_ENCRYPTION_KEY` (32 random bytes, base64) is required: the app exits 1 without it. Keep a backup of the key; never put it in chat or git. `BLOOMY_CONTENT_DIR` and `BLOOMY_IMAGES_DIR` are for tests only. `ZALOPAY_ENDPOINT` is required too (the sandbox address, deliberately). `BLOOMY_BASE_URL` and `ZALOPAY_ENDPOINT` are checked at start (exit 1, the variable's name and the reason only): each must be a bare https origin, no path, no trailing slash, no query or user name (http is accepted only for localhost, for development and the CI smoke test). `BLOOMY_BASE_URL` must be the real https address: it feeds canonical URLs, Open Graph tags and the sitemap, and a trailing slash would make the ZaloPay callback `//api/orders/ipn`, a 404.
- **What the app does at start, at stop and on every response [verified in `server.js` and `routes/` 2026-10-10]:** every response carries `X-Bloomy-Build`, the image tag (`BLOOMY_BUILD`, set from the CI build argument; `dev` outside CI). At start it logs `Bloomy: ZaloPay endpoint host: <host>` and, when a stored 2FA secret cannot be decrypted with the key, `Bloomy: ERROR: TOTP_ENCRYPTION_KEY cannot decrypt…` (section 4, owner 2FA). A missing variable or a bad URL exits 1 and prints names and reasons only, never values. On SIGTERM (`docker stop`, a compose swap) it stops taking connections, lets open requests finish, closes the database pool and exits 0 (`Bloomy: shut down cleanly`); if requests are still open after 8 s it exits 1. ZaloPay calls time out after 6 s. With no `settings` row the settings and flowers endpoints answer 503 `settings_missing` (`POST /api/orders/quote` still answers 500: known, unfixed); an impossible delivery date answers 400, not 500.
- **Deploy pipeline facts (verified on pgschema 1.13.1; the image is now 1.14.1, bumped by Dependabot on 2026-11-22, and CI re-checks only the empty plan and the offline plan, so the JSON details below were not re-verified on 1.14.1) [verified locally unless tagged]:** `plan --output-json` has `groups[].steps[]{sql,type,operation,path,directive?}`; one group is one transaction; no changes is `"groups": null`; `apply --plan` refuses a stale plan (fingerprint mismatch, exit 1); a role that cannot see the tables yields a WRONG plan, so plan as the owner. Invisible to `plan`: removing or reordering an enum value, column order, equivalent CHECK rewrites, so enum values are only ever added. Almost all DDL takes ACCESS EXCLUSIVE briefly and queues readers and writers of that table behind a waiting DDL for up to the lock timeout per attempt; other tables are unaffected. `--lock-timeout` is not applied to `CREATE INDEX CONCURRENTLY`; a new index plans as that statement plus a `pgschema:wait` group (verified 2026-10-10). A trailing slash in `BLOOMY_BASE_URL` gives a callback that returns 404. `docker stop` exits 0 now (it was 143).
- Where a failed deploy stops decides what is left: before the swap the old container keeps serving; after it the site stays down until the rollback finishes. After a schema change a rollback is the image only; you fix forward.

### Pipeline decisions (2026-10-10)

- **The schema apply is confirmed by a human and never rolled back: fix forward.** The previous app must therefore run on the new schema; the gate checks that.
- **The gate is a default-deny allow-list over the plan JSON**, not "grep for DROP": the exit code carries no signal, multi-group plans leave partial state, and an enum removal is invisible to `plan`.
- **The embedded PostgreSQL is baked into the schema image.** No second database and no internet at deploy time; CI plans on a network with no route out to prove it.
- **Seeds ride in the schema image, not the app image.** The app image is code only; database content travels with the database tools.
- **ZaloPay is sandbox for good**, so `ZALOPAY_ENDPOINT` is explicit and required.
- **Lock timeout 2 s** (`--lock-timeout`); an outage of up to about 10 s at the swap is accepted; no deploy window.
- **The https rule is host-based** (https, except http for localhost), not tied to `NODE_ENV`: the image forces `NODE_ENV=production` and CI uses `http://localhost:3000`.
- **The TOTP startup check logs and never exits**: a wrong 2FA key must not take the storefront down. ZaloPay calls time out at 6 s; a SIGTERM handler finishes open requests (8 s ceiling).
- **Base images are pinned by tag and digest (2026-11-22):** the three `node` FROM lines and `pgplex/pgschema`. To bump: pick the new tag, read its digest with `docker buildx imagetools inspect <tag>`, change tag and digest together, run `ci_dryrun.py`. `.github/dependabot.yml` (docker, weekly, no major jumps) opens a PR for a newer tag; it does not notice a republished tag with the same version, It does scan `Dockerfile.schema`: its first pull request (#27) bumped `pgplex/pgschema` 1.13.1 to 1.14.1, tag and digest together; CI on `main` passed the schema steps and every suite, and H deployed it to staging and prod on 2026-11-22 (both healthy) [stated]. Wait for a bump's own CI run before merging it.
- **Never built, undecided:** an `[allow-drop]` marker in CI; an upgrade test (one write suite versus all of them).

## 10. TESTS AND ACCEPTANCE CRITERIA

## 12. TESTING PRACTICE AND FINDINGS

**Cross-browser check (2026-11-20, `tests/cross_browser_check.mjs`; not a suite, not in CI):** Firefox 160 through WebDriver BiDi (own profile, no display) and WebKitGTK through MiniBrowser under WebKitWebDriver on a private Xvfb, no package needed. Per browser at 1440, 390 and 360 px: the list's columns, 20 cards and no sideways scroll, the page bar on one line, page 2 by a click that reaches the button, the Valentine filter and its "Dịp" chips, a product's add to cart and the cart badge, the cart, the checkout form, the home page, and every other page type for sideways scroll, scripts and broken pictures (see "Closed everywhere" below); Firefox's log is checked for JavaScript errors. WebKit gets the site through a small proxy that drops one CSP directive, `upgrade-insecure-requests` (WebKit upgrades even http://localhost to https, which a local server cannot answer); the rest of the policy is still enforced. **What it found [verified]:** on a phone the cart and checkout pages scrolled sideways (51-69 px at 390 in WebKit and Firefox, 12-24 px at 360) because a bare `1fr` grid column cannot shrink below its content (a 560 px photo; the checkout form): fixed with `minmax(0, 1fr)` in `cart.css` and `checkout.css`. **Closed everywhere (2026-11-20):** the sweep now visits every page type (the sitemap's pages, the blog posts, the sign-in page, an order page, 13 kinds of product page by status, type, style and size count, and a three-line cart) and found no other customer page that scrolled sideways, but 49 other bare `fr` grid columns in 10 customer stylesheets were a latent risk, so they were all changed to `minmax(0, ...)` mechanically (by a parenthesis-aware script, so nothing already inside `minmax` was touched). Proof it changes nothing else: 198 screenshots (3 widths x 2 engines x every page) before and after are pixel-identical apart from timing noise that also appears between two runs of the same CSS (lazy images, the add-to-cart button's transition) and the intended sign-in fix. `ui_polish_test` now fails on any bare `fr` in a customer stylesheet (the admin stylesheets, behind a login, were not changed and are not held to it). The sign-in page was too wide for a phone (a 340 px card plus 2 x 24 px padding): fixed. The 5-page bar wrapped at 360 px. Not covered: real Safari (fonts, the iPhone toolbar, touch, the date picker), real phones, the dark theme.

(The notes for rebuilding the old chat sandbox were removed: suites now run against the real local Docker stack, see `CLAUDE.md`.)

**Mutation controls (how every suite was proven to bite):** copy each file to be mutated to a scratch folder as `mut_<full path with / replaced by _>.bak`; apply a one-line change with an `assert text.count(old) == 1`-style guard that **aborts the run if the change did not apply**; run the suite; check the expected `FAIL` lines; restore from the backup; **rebuild the database after every run** (a destructive mutation can delete seeded rows and poison the next run); finally `cmp` every file with its backup. **Never name backups by basename** — two files named `admin-campaigns.js` (the route and the page script) once overwrote each other's backup and the "restore" put client code over the server route; the symptom was later runs printing nothing at all.

**Quirks and findings worth keeping**
- **jsdom:** no layout engine and **no real CSS cascade** (tests stub `.css` requests), no `showModal`/`close` (polyfill on `HTMLDialogElement.prototype`), navigation is "not implemented", `window.isSecureContext` is undefined (the code treats `undefined` as "ok"), `requestAnimationFrame` exists only with `pretendToBeVisual: true`, `getComputedStyle` is unreliable for the cascade. Pages are loaded with `runScripts: "dangerously"`, a CSS-stubbing resource interceptor and a `beforeParse` hook that installs `fetch` (adds the session cookie) and, when needed, **captures `setTimeout`/`clearTimeout`** so a 5 s / 10 s timer can be inspected and fired instantly. **Wait for the page's scripts before clicking** (`until(() => w.Bloomy)`): a click before `main.js` ran silently does nothing — this caused four false failures.
- **A check that only reads the `hidden` property cannot see a CSS rule that overrides it.** Use static CSS assertions for visibility rules and say that real rendering is unverified.
- **A "wait for X" check can pass on an earlier draw.** When a click triggers a reload, wait for the reload (count the requests) before marking or measuring the DOM.
- A page script's rejected promise after the test ends crashes Node: tests install `process.on("unhandledRejection")` and count it as a failure; wait for in-flight page requests before killing a test's own server.
- pgschema: `plan` and `apply` start an embedded PostgreSQL to check `schema.sql` against; `Dockerfile.schema` now fetches it once, at image build (Maven Central, checksum-verified), so a deploy-time `plan` needs no internet. When the `FROM pgplex/pgschema` tag is bumped, change the digest, the embedded version and the checksum with it. `plan --output-json` has one entry per transaction; its exit code is 0 with or without changes (no-changes case re-checked 2026-10-10: `"groups": null`), so a gate must read the JSON. A new CHECK on a table with violating rows fails at VALIDATE and leaves the database half-applied; new NOT NULL columns need DEFAULTs. A column rename plans as DROP + ADD.
- ZaloPay and Google are unreachable: tests cover `zalopay_error` and signed IPNs (HMAC-SHA256 with `ZALOPAY_KEY2`, sandbox value `b`); GA is covered by headers + loader behaviour only.
- Any local server needs `TOTP_ENCRYPTION_KEY` (32 bytes, base64); for `twofa_test` export the same value to the suite.
- Rate limits: the limiters live in the server's memory (orders 20 per 15 min). `npm test` (`tests/run_all.mjs`, added 2026-11-20) starts a fresh server and a throwaway database per run, so back-to-back full runs are fine [verified: two in a row, 1,455 checks each, 0 failed, no database left behind, the dev database unchanged]; a suite run by hand against a long-running server still shares its budget.
- Findings worth remembering: equal-specificity CSS rules are decided by source order (the menu bug); `.btn` etc. set `display`, so `hidden` needs the global rule; `[id] { scroll-margin-top }` already exists (don't add `scroll-padding`); `scrollTo({behavior:"smooth"})` ignores the CSS reduced-motion rule (decide in JS); an element at `opacity: 0` is not counted as painted (LCP) — start animations at ≥ 0.4; a folder named `x.webp` passes an extension check — list files only; the GA ID/hostname gate keeps local runs out of the real property.
